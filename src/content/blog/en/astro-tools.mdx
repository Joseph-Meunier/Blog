## Tool 1 — Astro Content Collections

**Content Collections** are the foundation of the article system. They load Markdown and MDX files and validate their frontmatter against a schema.

The blog collection is defined in `src/content.config.ts`:

```ts
import { defineCollection, z } from 'astro:content';
import { glob } from 'astro/loaders';

const blog = defineCollection({
  loader: glob({
    base: './src/content/blog',
    pattern: '**/*.{md,mdx}',
  }),
  schema: ({ image }) => z.object({
    title: z.string(),
    description: z.string(),
    startDate: z.coerce.date(),
    pubDate: z.coerce.date(),
    updatedDate: z.coerce.date(),
    heroImage: image(),
    isPublished: z.boolean(),
    tags: z.array(z.string()).optional(),
    readingTime: z.string().optional(),
  }),
});

export const collections = { blog };
```

### What this tool provides

- A shared structure for every article.
- Validation for dates, images, tags and publication states.
- Clear errors during the build.
- A typed API through `getCollection('blog')`.

The three dates have distinct meanings:

- `startDate`: when writing started.
- `pubDate`: when the article was published.
- `updatedDate`: the latest update.

The layout must use the correct field for each card. Displaying `pubDate` under “Written on” produces incorrect information even though the build remains valid.

## Tool 2 — MDX

**MDX** combines Markdown syntax with JSX and Astro components.

An article begins with its frontmatter:

```mdx
---
title: 'The Astro tools used to build this blog'
startDate: '2025-11-07'
pubDate: '2025-08-11'
updatedDate: '2026-08-11'
isPublished: false
---
```

The rest of the file contains headings, lists, links, images and code blocks. MDX can also import a constant or component when an article needs more advanced behavior.

### When should MDX be used?

MDX is useful for:

- Embedding an interactive component in an article.
- Rendering conditional content.
- Reusing an existing Astro component.
- Keeping a Markdown-like syntax for editorial content.

A plain `.md` file is enough for a purely editorial post. This project uses `.mdx` to keep the option of enriching tutorials later.

## Tool 3 — Astro dynamic routes

Files inside `src/pages` define public URLs. Bracketed segments are dynamic:

```text
src/pages/[lang]/blog/[...slug].astro
```

This single page can generate:

```text
/fr/blog/astro-tools/
/en/blog/astro-tools/
```

Each collection ID is converted into route parameters:

```ts
const [lang, ...slugParts] = post.id.split('/');

return {
  params: {
    lang,
    slug: slugParts.join('/'),
  },
  props: post,
};
```

The `[...slug]` segment also supports nested slugs. Content identified as `en/guides/astro-tools` could generate `/en/blog/guides/astro-tools/`.

## Tool 4 — The blog i18n system

Translations are separate, complete files:

```text
src/content/blog/
├── fr/
│   └── astro-tools.mdx
└── en/
    └── astro-tools.mdx
```

Astro generates the IDs `fr/astro-tools` and `en/astro-tools`.

The blog list filters the collection using the route language:

```ts
const posts = allPosts
  .filter((post) => post.id.startsWith(`${lang}/`))
  .filter((post) =>
    !isProd ||
    (post.data.isPublished && post.data.pubDate <= new Date())
  )
  .sort((a, b) =>
    b.data.pubDate.valueOf() - a.data.pubDate.valueOf()
  );
```

The English page should not silently display French posts. Each translation needs its own title, description, tags, table of contents and body.

Astro also documents how to [use content collections for translated content](https://docs.astro.build/en/recipes/i18n/#use-collections-for-translated-content).

## Tool 5 — `import.meta.env.BASE_URL`

`BASE_URL` creates links that work both at a domain root and within a subdirectory such as a GitHub Pages project site.

```ts
const siteBase = import.meta.env.BASE_URL.replace(/\/$/, '');
```

The language must be separated from the slug when building an article URL:

```ts
const [postLang, ...slugParts] = post.id.split('/');
const slug = slugParts.join('/');
const url = `${siteBase}/${postLang}/blog/${slug}/`;
```

Segment order matters:

```text
Incorrect: /blog/en/astro-tools/
Correct:   /en/blog/astro-tools/
```

The same base path should be used for favicons, fonts, sitemaps and other resources from `public/`.

## Tool 6 — The status page

The `/status` page is an internal project tool. It uses `getCollection` to display every article, including drafts and translations.

It shows:

- The hero image.
- The language.
- The title.
- The publication state.
- The creation date.
- The publication date.
- The update date.

Links are generated by a dedicated function:

```ts
const postUrl = (id: string) => {
  const [lang, ...slugParts] = id.split('/');
  return `${siteBase}/${lang}/blog/${slugParts.join('/')}/`;
};
```

This prevents table links from pointing to `/blog/en/...` instead of `/en/blog/...`. The language column distinguishes translations that share a slug.

## Tool 7 — `BaseHead` and SEO

The `BaseHead.astro` component centralizes the contents of the page `<head>`:

- Title and description.
- Canonical URL.
- Social preview image.
- Open Graph metadata.
- Article metadata such as dates and tags.
- Favicon, fonts and sitemap.

Centralizing these values avoids repeating tags across pages and keeps their structure consistent.

[Astro SEO](https://github.com/jonasmerlin/astro-seo#readme) is another option for generating this metadata. The current component already covers the blog’s main requirements, although `hreflang` links between translations remain a possible improvement.

## Tool 8 — Lucide Astro

[Lucide Astro](https://lucide.dev/guide/packages/lucide-astro) provides SVG icons as components.

```astro
---
import { Moon, Sun } from 'lucide-astro';
---

<button aria-label="Change theme">
  <Sun class="sun-icon" />
  <Moon class="moon-icon" />
</button>
```

This is easier to read than copying the complete contents of each SVG. Icons also share a coherent visual style and remain customizable with CSS.

## Tool 9 — The validation command

The final tool is the Astro build itself:

```bash
npm run build
```

This command:

- Validates the collection schema.
- Compiles MDX files.
- Generates French and English routes.
- Optimizes images.
- Produces static files inside `dist/`.

After adding a translation, its route should appear in the build output. The file must also be tracked by Git:

```bash
git status --short
```

An article available locally but missing from Git will not appear in a deployment built from the repository.

## Conclusion

Each tool has a clear responsibility:

- **Content Collections** structure and validate posts.
- **MDX** enriches content.
- **Dynamic routes** generate static pages.
- **The i18n system** keeps translations genuinely separate.
- **BASE_URL** makes links reliable locally and in production.
- **The status page** provides content oversight.
- **BaseHead** centralizes SEO.
- **Lucide Astro** simplifies icons.
- **The Astro build** validates everything before deployment.

This separation makes the blog easier to understand, test and extend.
