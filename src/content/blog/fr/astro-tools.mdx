## Outil 1 — Astro Content Collections

Les **Content Collections** sont le cœur de la gestion des articles. Elles chargent les fichiers Markdown et MDX, puis valident leur frontmatter avec un schéma.

La collection du blog est définie dans `src/content.config.ts` :

```ts
import { defineCollection, z } from 'astro:content';
import { glob } from 'astro/loaders';

const blog = defineCollection({
  loader: glob({
    base: './src/content/blog',
    pattern: '**/*.{md,mdx}',
  }),
  schema: ({ image }) => z.object({
    title: z.string(),
    description: z.string(),
    startDate: z.coerce.date(),
    pubDate: z.coerce.date(),
    updatedDate: z.coerce.date(),
    heroImage: image(),
    isPublished: z.boolean(),
    tags: z.array(z.string()).optional(),
    readingTime: z.string().optional(),
  }),
});

export const collections = { blog };
```

### Ce que cet outil apporte

- Une structure commune pour tous les articles.
- Une validation des dates, images, tags et statuts.
- Des erreurs explicites pendant le build.
- Une API typée avec `getCollection('blog')`.

Les trois dates ont des rôles différents :

- `startDate` : début de rédaction.
- `pubDate` : publication.
- `updatedDate` : dernière modification.

Le layout doit utiliser le bon champ pour chaque carte. Afficher `pubDate` dans « Écrit le » donnerait une information incorrecte même si le build reste valide.

## Outil 2 — MDX

Le format **MDX** combine la simplicité de Markdown avec la possibilité d’utiliser du JSX et des composants Astro.

Un article commence par son frontmatter :

```mdx
---
title: 'Les outils Astro utilisés pour construire ce blog'
startDate: '2025-11-07'
pubDate: '2025-12-07'
updatedDate: '2026-08-11'
isPublished: false
---
```

Le reste du fichier contient des titres, des listes, des liens, des images et des blocs de code. MDX permet aussi d’importer une constante ou un composant lorsque l’article a besoin d’un comportement plus avancé.

### Quand utiliser MDX ?

MDX est utile pour :

- Intégrer un composant interactif dans un article.
- Afficher un contenu conditionnel.
- Réutiliser un composant Astro existant.
- Conserver une syntaxe proche de Markdown pour le texte.

Pour un article purement éditorial, un fichier `.md` peut suffire. Ici, `.mdx` garde la possibilité d’enrichir les tutoriels plus tard.

## Outil 3 — Les routes dynamiques Astro

Les fichiers placés dans `src/pages` définissent les URLs publiques. Les segments entre crochets sont dynamiques :

```text
src/pages/[lang]/blog/[...slug].astro
```

Cette seule page peut générer :

```text
/fr/blog/astro-tools/
/en/blog/astro-tools/
```

Pour chaque article, l’identifiant de collection est transformé en paramètres :

```ts
const [lang, ...slugParts] = post.id.split('/');

return {
  params: {
    lang,
    slug: slugParts.join('/'),
  },
  props: post,
};
```

Le segment `[...slug]` accepte aussi des slugs imbriqués. Un contenu identifié par `fr/guides/astro-tools` pourrait ainsi produire `/fr/blog/guides/astro-tools/`.

## Outil 4 — Le système i18n du blog

Les traductions sont de vrais fichiers séparés :

```text
src/content/blog/
├── fr/
│   └── astro-tools.mdx
└── en/
    └── astro-tools.mdx
```

Astro génère alors les identifiants `fr/astro-tools` et `en/astro-tools`.

La liste du blog filtre la collection selon la langue de la route :

```ts
const posts = allPosts
  .filter((post) => post.id.startsWith(`${lang}/`))
  .filter((post) =>
    !isProd ||
    (post.data.isPublished && post.data.pubDate <= new Date())
  )
  .sort((a, b) =>
    b.data.pubDate.valueOf() - a.data.pubDate.valueOf()
  );
```

Il ne faut pas afficher automatiquement le français sur la page anglaise. Une traduction doit contenir son propre titre, sa description, ses tags, son sommaire et son contenu.

La documentation Astro détaille également comment [utiliser les collections pour du contenu traduit](https://docs.astro.build/en/recipes/i18n/#use-collections-for-translated-content).

## Outil 5 — `import.meta.env.BASE_URL`

`BASE_URL` permet de construire des liens qui fonctionnent aussi bien à la racine d’un domaine que dans un sous-dossier, par exemple sur GitHub Pages.

```ts
const siteBase = import.meta.env.BASE_URL.replace(/\/$/, '');
```

Pour créer l’URL d’un article, il faut séparer la langue du slug :

```ts
const [postLang, ...slugParts] = post.id.split('/');
const slug = slugParts.join('/');
const url = `${siteBase}/${postLang}/blog/${slug}/`;
```

L’ordre des segments est important :

```text
Incorrect : /blog/en/astro-tools/
Correct   : /en/blog/astro-tools/
```

La même base doit être utilisée pour les favicons, polices, sitemaps et autres ressources de `public/`.

## Outil 6 — La page de statut

La page `/status` est un outil interne au projet. Elle utilise `getCollection` pour afficher tous les articles dans un tableau, y compris les brouillons et les traductions.

Elle affiche :

- L’image principale.
- La langue.
- Le titre.
- Le statut.
- La date de création.
- La date de publication.
- La date de mise à jour.

Le lien est construit par une fonction dédiée :

```ts
const postUrl = (id: string) => {
  const [lang, ...slugParts] = id.split('/');
  return `${siteBase}/${lang}/blog/${slugParts.join('/')}/`;
};
```

Cette fonction évite que les liens du tableau pointent vers `/blog/en/...` au lieu de `/en/blog/...`. La colonne de langue distingue les traductions qui partagent le même slug.

## Outil 7 — `BaseHead` et le SEO

Le composant `BaseHead.astro` centralise les informations de la balise `<head>` :

- Le titre et la description.
- L’URL canonique.
- L’image sociale.
- Les métadonnées Open Graph.
- Les métadonnées d’article comme les dates et les tags.
- Le favicon, les polices et le sitemap.

Cette centralisation évite de répéter les mêmes balises sur chaque page et garantit une structure cohérente.

[Astro SEO](https://github.com/jonasmerlin/astro-seo#readme) est une alternative intéressante pour générer ces métadonnées. Le composant actuel couvre déjà les besoins principaux du blog, mais les liens `hreflang` entre traductions restent une amélioration possible.

## Outil 8 — Lucide Astro

[Lucide Astro](https://lucide.dev/guide/packages/lucide-astro) fournit des icônes SVG sous forme de composants.

```astro
---
import { Moon, Sun } from 'lucide-astro';
---

<button aria-label="Changer de thème">
  <Sun class="sun-icon" />
  <Moon class="moon-icon" />
</button>
```

Cela rend le code plus lisible que de copier le contenu complet de chaque SVG. Les icônes partagent également le même style graphique et restent personnalisables avec CSS.

## Outil 9 — La commande de validation

L’outil final est simplement le build Astro :

```bash
npm run build
```

Cette commande :

- Valide le schéma des collections.
- Compile les fichiers MDX.
- Génère les routes françaises et anglaises.
- Optimise les images.
- Produit les fichiers statiques dans `dist/`.

Après l’ajout d’une traduction, le journal doit afficher la nouvelle route. Il faut aussi vérifier que le fichier est suivi par Git :

```bash
git status --short
```

Un article présent localement mais non ajouté à Git ne sera pas inclus dans un déploiement construit depuis le dépôt.

## Conclusion

Chaque outil répond à une responsabilité précise :

- **Content Collections** structure et valide les articles.
- **MDX** enrichit le contenu.
- **Les routes dynamiques** génèrent les pages statiques.
- **Le système i18n** sépare réellement les traductions.
- **BASE_URL** sécurise les liens en local et en production.
- **La page de statut** contrôle le contenu.
- **BaseHead** centralise le SEO.
- **Lucide Astro** simplifie les icônes.
- **Le build Astro** vérifie l’ensemble avant le déploiement.

Cette séparation rend le blog plus facile à comprendre, tester et faire évoluer.
