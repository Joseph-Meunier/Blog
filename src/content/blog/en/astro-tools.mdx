## Content collections

Astro content collections load Markdown and MDX files while validating their metadata with a TypeScript schema.

This project recursively loads every article inside `src/content/blog`:

```ts
import { defineCollection, z } from 'astro:content';
import { glob } from 'astro/loaders';

const blog = defineCollection({
  loader: glob({
    base: './src/content/blog',
    pattern: '**/*.{md,mdx}',
  }),
  schema: ({ image }) => z.object({
    title: z.string(),
    description: z.string(),
    pubDate: z.coerce.date(),
    updatedDate: z.coerce.date(),
    startDate: z.coerce.date(),
    heroImage: image(),
    isPublished: z.boolean(),
    tags: z.array(z.string()).optional(),
    readingTime: z.string().optional(),
  }),
});

export const collections = { blog };
```

This schema prevents incomplete content from being published. Astro reports an invalid date, missing image or incorrectly typed field during the build.

## Organizing posts by language

Translations live in two directories and share the same slugs:

```text
src/content/blog/
├── fr/
│   ├── astro-blog.mdx
│   └── astro-tools.mdx
└── en/
    ├── astro-blog.mdx
    └── astro-tools.mdx
```

The content IDs generated by Astro include the language:

```text
fr/astro-tools
en/astro-tools
```

Every translation is a real article. The English page does not silently reuse French content: its title, description, tags, table of contents and body are translated.

This structure also lets a translation be published later, provided the interface handles a temporarily missing language.

## Generating the post list

The `src/pages/[lang]/blog/[...page].astro` page reads the language from the URL and filters the collection:

```ts
const allPosts = await getCollection('blog');

const posts = allPosts
  .filter((post) => post.id.startsWith(`${lang}/`))
  .filter((post) =>
    !isProd ||
    (post.data.isPublished && post.data.pubDate <= new Date())
  )
  .sort(
    (a, b) => b.data.pubDate.valueOf() - a.data.pubDate.valueOf()
  );
```

Drafts and scheduled posts remain visible during development. Production only displays published posts whose publication date has passed.

The results are then passed to `paginate`:

```ts
return paginate(posts, {
  params: { lang },
  pageSize: 10,
});
```

## Building localized URLs

A content ID is not directly a public URL. For `en/astro-tools`, the expected route is `/en/blog/astro-tools/`, not `/blog/en/astro-tools/`.

The language must be separated from the slug:

```ts
const [postLang, ...slugParts] = post.id.split('/');
const slug = slugParts.join('/');
const url = `${siteBase}/${postLang}/blog/${slug}/`;
```

The blog list and status page now apply this rule. Moving it into a shared utility would be a useful improvement if more pages need to generate the same links.

## Generating individual post pages

The dynamic route `src/pages/[lang]/blog/[...slug].astro` generates a static page for every collection entry.

The content ID is converted into route parameters:

```ts
const [lang, ...slugParts] = post.id.split('/');

return {
  params: {
    lang,
    slug: slugParts.join('/'),
  },
  props: post,
};
```

Astro can then build both variants:

```text
/fr/blog/astro-tools/
/en/blog/astro-tools/
```

These are real static pages: fast to serve and easy for search engines to index.

## Handling the base path

A site deployed inside a subdirectory—for example on GitHub Pages—cannot assume its root is always `/`.

Astro exposes the configured path through `import.meta.env.BASE_URL`:

```ts
const siteBase = import.meta.env.BASE_URL.replace(/\/$/, '');
```

It can then prefix generated URLs:

```ts
const url = `${siteBase}/${lang}/blog/${slug}/`;
```

This works locally with `/` and in production with a path such as `/Blog/`. The same principle applies to favicons, fonts, sitemaps and other files placed in `public/`.

## Building a status page

The `/status` page displays every article, including drafts and translated versions. It provides a quick way to inspect:

- The article language.
- Its state: draft, scheduled or published.
- Its creation, publication and update dates.
- Its hero image.
- The link to the generated page.

A dedicated function prevents the language and `blog` segments from being reversed:

```ts
const postUrl = (id: string) => {
  const [lang, ...slugParts] = id.split('/');
  return `${siteBase}/${lang}/blog/${slugParts.join('/')}/`;
};
```

Adding a language column also makes rows with identical slugs easy to distinguish.

## Additional tools

### Internationalization

Astro documents how to [use content collections for translated content](https://docs.astro.build/en/recipes/i18n/#use-collections-for-translated-content).

### SEO

[Astro SEO](https://github.com/jonasmerlin/astro-seo#readme) can simplify metadata generation. In this blog, the `BaseHead` component already centralizes the page title, description, social image and Open Graph information.

A bilingual site should also expose `hreflang` links between the French and English versions.

### Icons

[Lucide Astro](https://lucide.dev/guide/packages/lucide-astro) provides consistent SVG icons as components, avoiding large inline SVG blocks throughout the codebase.

## Mistakes to avoid

### Creating files without adding them to Git

Astro may detect a local MDX file even though it remains absent from the deployment when Git does not track it.

```bash
git status --short
git add src/content/blog/en
```

Always confirm that new translations are included in the commit sent to the deployment server.

### Using the wrong route order

```text
Incorrect: /blog/en/astro-tools/
Correct:   /en/blog/astro-tools/
```

The content directory structure must not be blindly appended to the page route.

### Placing styles outside the head

A `<style>` block placed between `</head>` and `<body>` produces invalid HTML. Depending on the browser or security policy, those styles may not apply.

Page-specific styles belong inside `<head>`. Shared or essential rules are often safer in a global stylesheet compiled by Astro.

### Forgetting to rebuild after adding content

The final verification is straightforward:

```bash
npm run build
```

The build output should list every expected French and English route.

## Conclusion

Astro makes a multilingual blog relatively straightforward as long as three concepts remain separate: the content ID, the public route and the deployment base path.

Collections validate the data, the `fr` and `en` directories organize translations, dynamic routes generate the pages, and the status screen provides a global view of the content. This foundation can now be extended with `hreflang` metadata and automatic detection of missing translations.
